---
name: design-system
description: Load design tokens and structural skeletons for one or more curated design references from the design-reference library, grouped by block type (header, hero), and use them to generate on-brand UI code with low drift from the source references. Use when the user runs /design-system, pastes a config id (cfg_...), names curated reference ids (e.g. stripe-header, linear-hero), asks to build a page/header/hero using the design-reference library or a saved design-reference config, or wants to swap just one block (e.g. "change the header, keep the hero") on a page already generated this way.
argument-hint: "[reference-id...] | [config-id]"
---

## Arguments

A saved config id from the web gallery, or reference ids to use directly, space-separated, plus whatever else the user said in plain language: $ARGUMENTS

## Instructions

1. Take the reference ids (or the single `cfg_...` config id) out of $ARGUMENTS. Ignore this step's output for step 2 below — it's just the ids.
1a. If the user is asking to swap only some block(s) of a page you (or a prior run) already generated — "поменяй хэдер на X, остальное оставь", "swap the hero", "try a different header" — don't make them restate every reference id. Read the persisted `.design-system.json` (step 9 of the run that made the current page; if you don't see one, ask where the previous config lives before guessing). Take the `reference` id already recorded there for every block they *didn't* mention, combine it with the new id(s) for the block(s) they did mention, and use that full list in step 3. Reuse the persisted `_theme_anchor` value unless they also asked to change it — pass it explicitly so it doesn't silently re-default to "hero". If the block being swapped is itself the current anchor, tell the user before proceeding: swapping it changes the shared color/font for every *other* block too (a new anchor donates new values) — that's expected fallout, not a bug, but they should know before you regenerate. When you write the result back, only replace the swapped block's markup/CSS/copy — leave every other block's already-generated code exactly as it was (touch its color/font values too, but only if the anchor itself changed).
2. If the remaining text says which block should set the color theme (e.g. "let the header set the colors", "keep it stripe's white", "match the hero"), resolve that to one of the requested block types and pass it as `theme_anchor`. Otherwise pass no `theme_anchor` — a sensible default still applies with zero input from the user (see step 4), which is the common case.
3. If $ARGUMENTS resolved to a single `cfg_` id, call the `resolve_config` tool with that id (and `theme_anchor` if set in step 2). Otherwise call `get_design_system` with the reference ids as a list (and `theme_anchor` if set).
4. `get_design_system`/`resolve_config` normalize every block's background/text/accent colors and typography's font_family to match the anchor block, so blocks always compose without a light/dark seam, two clashing accent hues, or mismatched type. Each block keeps its own radii and shadows — that's a reference's structural signature (e.g. fully-round pill buttons vs. sharp corners), not shared surface — plus its own structure (skeleton) and component-specific sizes/spacing. The result's `_theme_anchor` key says which block type was actually used as the anchor — **read it from the response, don't assume or guess (e.g. don't assume "hero" when nothing was passed)**: a `cfg_` id can carry its own saved default from the gallery, which can differ from the plain "hero, else alphabetically first" fallback. When you tell the user what happened, name the actual `_theme_anchor` value and be clear that it set the shared surface (including accent) — each block's own radii/shadows still came from its own reference. Don't ask the user to pick an anchor up front; only act on it if they mention one, and only re-run with a different `theme_anchor` if they ask to change it after seeing the result.
5. If the tool call fails because a reference id is unknown, call `list_references` to show the user what's available and ask them to pick again. If it fails because the config id is unknown, tell the user the link may have expired and point them back to the gallery. If it fails because of an unknown `theme_anchor`, tell the user which block types were actually requested and ask in plain language which one should set the theme.
6. For each block type returned (e.g. `header`, `hero` — everything except the `_theme_anchor` key handled in step 4), use its `skeleton` as the structural scaffold and its `tokens` as the concrete values (colors, typography, spacing, radii, shadows, `gradient` when present — a background glow/gradient effect, separate from `shadows`; most references won't have it — and `motion` when present, covering `hover`, `entrance`, `ambient`, `scroll`, and `cursor` animation, keyed by element type) when generating that block's code. Do not invent structure or values outside what these two fields specify — **this includes a non-anchor block's own `radii`/`shadows`: always use their exact values on that block's elements (e.g. the corner radius of its own `cta_button`), even where they'd look more "consistent" matched to the anchor block's shape. Never quietly substitute the anchor's radius/shadow instead because it "looks more unified" — that's silent drift, exactly what this plugin exists to avoid.** (Color, including accent, genuinely is shared via `theme_anchor` — that one's intentional, not drift.) If a non-anchor block's radii/shadows genuinely look inconsistent next to the anchor's, say so to the user as a data-quality/design observation rather than fixing it yourself unasked. Also don't invent elements the skeleton doesn't list (e.g. a subtext paragraph or a second CTA button) even if that's a common pattern for this kind of block — the skeleton's `elements` array is the exact, complete structure.
7. Some non-`header` block's skeleton carries its own page-chrome elements — a `logo` plus `nav`/`icon_button`, usually signaled by a `layout` string containing something like `top-nav-overlay` (that reference's own real site has no separate header — the block doubles as one, e.g. a hero with nav overlaid on its photo). If a separate `header` block is also being composed, it already owns the page's nav — skip that other block's own `logo`/`nav`/`icon_button` elements (its remaining elements — headline, subtext, cta_button, rating, carousel, etc. — still render exactly as specified) and tell the user you dropped them and why, so two nav bars don't stack. If no separate `header` block is being composed, render that block's chrome elements as-is — it's the only header the page has.
7a. **Ask a design-thinking round before generating — the references fix the aesthetic direction, they don't supply the product context, and you may not guess it silently.** frontend-design's core move is asking before building; this plugin kept the aesthetic direction (the references) but lost the questions. Restore them. Before writing any copy or detail, if the user's request doesn't already explicitly state them, ask a short round of questions covering the four things a reference can't tell you: (1) **purpose** — what does this exact page/block do, and what is the user's one task here; (2) **audience** — who is actually using this, in their vocabulary, not a pitch-deck register; (3) **tone** — the mood the block should land, given the reference's character; (4) **differentiation** — the one detail a visitor should remember after one second. Ask them up front as a question round (a couple of pointed questions), not after you've already drafted. If the user already supplied these in their message, don't re-ask — just state the direction you landed on in one sentence before you start so they can catch a misread early. Only fall back to deriving from a `README`/`package.json`/the app's own copy when the user explicitly points you at a project and declines to answer — never as the default. This step exists because the plugin's job is low drift to the *reference* — but low drift still permits, and the skill requires, writing copy and detail that no other product could get away with.
8. **Tokens and skeleton fix structure and base styling — they say nothing about copy, type pairing, or component detail. That's still on you, and getting it wrong is what makes an otherwise faithful reproduction read as generic AI output anyway:**
   - **Copy is not the tool's job to derive, but it's still your job to make good.** Never reach for stock AI-marketing phrasing — "seamless", "empower", "unlock", "supercharge", "next-level", "revolutionize", "game-changing", generic "Get Started"/"Learn More" with no specifics. Ground every headline and button label in what this exact product/page actually does and who's using it, in their vocabulary, not a generic pitch-deck register. Be specific rather than clever. If you can't tell this headline apart from a headline for a different product in the same category, rewrite it.
   - **A single shared `font_family` is a brand anchor, not a full type system.** Uniform weight/size on everything reads flat. Build a real type scale from it: deliberate contrast between the headline (often heavier weight, tighter letter-spacing, larger jump in size than the "safe" default) and body/nav/label text (clearly distinct weight and size step, not a slight variation). If the reference's own real site pairs a display treatment with a plainer body face, prefer matching that pairing over forcing one family to do every job.
   - **Two faces when the reference has two: use the shared `display_font` for display/headline roles and the shared `font_family` for body/nav/labels — never run both through the same family's weights.** The `theme_anchor` already shares both faces across blocks, so a header and a hero in one page use the same pairing; the pairing is the brand, the scale (sizes, weights, tracking) is still yours to build per block. If `display_font` is absent, one family does everything and the contrast has to come from weight/size/letter-spacing — that's fine, that's the reference's choice.
   - **A generic font token is a gap in the data, not a license to ship generic type.** If the resolved `font_family` (or `display_font`) is a bare fallback stack — `system-ui`, `-apple-system`, `Arial`, `Helvetica`, `Roboto`, `"Segoe UI"`, plain `sans-serif`/`serif` — that almost always means the reference's real face wasn't identifiable, and shipping it verbatim is exactly the "generic AI output" this plugin exists to avoid. Pick a distinctive pairing that fits the reference's character (serif display + clean body, a tight grotesk, etc.) instead — but treat this as a **substitution, not a silent fix**: record what you chose and why in the `.design-system.json` you persist (step 9), so a follow-up run knows the token was replaced, and never reuse the exact same substitute for two different references (the whole point of the library is that each brand reads differently). If the token *is* a real, nameable family (e.g. `"Inter"`, `"Geist"`, `"Fraunces"`), use it exactly — no substitution.
   - **Don't ship placeholder-quality components — and for image-bearing elements, follow the right path for the type.** (Throughout this bullet, "available" means a tool already present in the session/environment — never install one to satisfy a check; treat it as unavailable and follow that path's own fallback instead.) A `mockup_image` element (a UI panel: chat interface, dashboard, code editor, stacked cards, etc.) is always hand-coded as real HTML/CSS/SVG matching its `style` description — never sourced as an image file. AI image generation reliably produces photography but unreliably produces legible on-screen UI text, so coding the mock yourself is both more reliable and more in your control: realistic example data (not lorem-ipsum-shaped filler), the same attention to spacing/borders/depth as the block's own tokens imply. A `background_image` element (photographic or textural: landscape, texture, abstract) is sourced as a real file through this fallback chain, trying the next step only if the previous one is unavailable or doesn't produce a usable result: (1) if an image-generation tool is available in this session, generate an image matching `style`; (2) otherwise, search for a suitable stock/CC-licensed photo (`WebSearch` or another available search tool), resolve its direct file URL, and download the bytes via `curl`/`wget` through Bash — `WebFetch` can locate and read the page but can't save binary content, so it's for finding the URL and checking the license, not for the download itself; (3) if neither worked, ask the user — supply their own file, or accept a flat gradient placeholder as a last resort (same reasoning as the gradient guidance below: a flat background is safer than a botched attempt). Never skip straight to a gradient without trying (1) and (2) first and never skip the ask in (3) — a silent gradient fallback is exactly the "placeholder-quality" outcome this bullet exists to prevent. For a file obtained via (1) or (2) — not one the user hands you directly in (3) — resize/compress it to a reasonable web size first: long edge around 1600–2000px, roughly under 300KB (an available tool like ImageMagick's `convert`/`magick`, `sips`, or `ffmpeg` can do this from the command line; an image-generation tool's own output is often already close to this size). If no resize tool is available, ship the file as-is but tell the user it's unoptimized rather than silently shipping an oversized original. However the file was obtained, save it wherever the project already keeps static assets (a framework's `public/`/`static/` directory, or a plain `./assets/` folder for a flat HTML page) and reference it the way the project already references its other images — never hotlink to an external URL, since that breaks the moment the source disappears or changes. A `background_video` element (a full-bleed autoplaying loop, `object-fit: cover`, `<video autoplay muted loop playsinline poster="...">` or the target framework's equivalent) is sourced through the same three-step chain as `background_image` — (1) a video-generation tool if available, (2) a stock/CC-licensed video found via `WebSearch`/an available search tool and downloaded via `curl`/`wget` (same `WebFetch`-can't-download-binaries caveat as images), (3) ask the user for their own file — except its last resort: if none of the three work, don't invent a placeholder video, downgrade the element to `background_image` instead (tell the user why) and run *that* type's own fallback chain from the top, gradient included if it comes to that. A sourced/generated video always ships `muted`, `loop`, `playsinline`, and `autoplay` (autoplay silently fails without `muted`), with its audio track stripped unconditionally (it's muted regardless, so audio is pure dead weight), resolution capped (around 1080p, lower if still large) and trimmed to a short loop (seconds, not minutes) — `ffmpeg` is the realistic tool for all of this, unlike the image tools above. Extract a poster frame (`ffmpeg -vframes 1` or equivalent), wire it into the `poster` attribute, and run it through the same image size/compression rule just described for `background_image` — a poster frame is an image once extracted, no separate rule needed. If no transcode tool is available, ship what you got and tell the user it's unoptimized, same posture as images — but with a ceiling: if the untranscoded file is more than a few MB, that's not "unoptimized," it's a real page-weight problem, so ask the user for a shorter/smaller clip (or a poster image to pair with it) instead of shipping it as-is, or downgrade to `background_image` if they'd rather skip video entirely. If a `scroll.scrub` entry targets an element that ends up downgraded from `background_video` to `background_image` this way, it has no `properties`/`from`/`to` to interpolate (those never applied to the video case) — drop the entry and tell the user, rather than inventing values for it. Any other decorative content (a generic icon-in-a-box feature card, etc.) still just needs real, on-topic detail rather than filler — one well-executed detail beats several generic ones.
   - **Implementing a `gradient` token: make it read as ambient light, not a stray shape.** Center it behind the element it's lighting (e.g. `left: 50%; transform: translateX(-50%)`), size it close to that element's own width, and use `filter: blur(...)` for softness rather than relying on a huge `box-shadow` blur radius alone. Check that no ancestor has `overflow: hidden` clipping it — a glow cut off at a hard edge reads as a rendering bug, not lighting. If you can't get it looking deliberate, a flat background is safer than a botched glow.
   - **Implementing a `texture` token: an overlay, not a background image.** Grain/noise/dots/grid render as a CSS/SVG overlay layered over the block's `background` (`mix-blend-mode` from `blend` if present, opacity from `opacity`), never as a shipped image file. Grain/noise use an inline SVG `feTurbulence` noise data-URI as the overlay's background; dots/grid use `repeating-radial-gradient` / `repeating-linear-gradient` sized by `size`. Keep it subtle — at the recorded `opacity`, a texture should add atmosphere (kill the flat-black/solid-color look) without reading as dirt on the screen. If it's genuinely invisible at a sane opacity, the token is noise — drop it rather than force it.
   - **Implementing `motion` tokens: match the given effect, invent nothing extra.** For each element type listed under `motion.hover`, apply a CSS `transition` using exactly the given `properties`/`duration`/`easing`, targeting the given `to` values on `:hover`/`:focus-visible` (and `:active` if the reference distinguishes it). For each element type under `motion.entrance`, animate it to its resting state on mount or on viewport-entry (plain CSS `@keyframes`+`animation`, an IntersectionObserver-driven class, or the target framework's native transition primitive — pick whatever fits the stack, the token specifies the effect, not the mechanism) using the given `type`/`duration`/`easing`/`delay`/`distance`. For each element type under `motion.ambient`, apply a CSS `animation` that loops forever from mount (`animation-iteration-count: infinite`, no trigger, no `:hover`/viewport condition) implementing the given `type` (e.g. `zoom` → a `@keyframes` alternating `transform: scale(1)`/`scale(var(--ambient-scale, 1.05))`) over `duration` with `easing`. For each element type under `motion.scroll`, implement `type: "parallax"` or `type: "scrub"` on the axis given by `axis` (`"y"` by default, `"x"` when specified) — prefer native CSS scroll-driven animations where the target supports them (`animation-timeline: scroll()` with a `@keyframes` moving the element by an amount scaled from `rate` for `parallax` — `scroll()` tracks the whole scrollable range, not any one element's viewport transit, matching `parallax`'s "keeps moving at any scroll position" behavior; `animation-timeline: view()` with a `@keyframes` built from `from`/`to`, mapping `range` to that view-timeline's `animation-range`, for `scrub` — `view()` tracks the subject element's own transit through the viewport, matching `scrub`'s default `"enters-to-exits-viewport"` range), falling back to a scroll listener + `requestAnimationFrame` computing the output from `rate * scrollY` or `rate * scrollX` per `axis` (`parallax`) or `clamp((scrollY - start) / (end - start), 0, 1)` interpolated across exactly the properties listed in `properties`, from their `from` values to their `to` values (`scrub`, over the span given by `range`) when broader compatibility or a framework's own primitive is needed. For each element type under `motion.cursor`: `type: "magnetic"` is a `pointermove` listener over the element (hit-area sized by `radius`) computing the cursor's offset from the element's center, scaling it by `strength` and clamping the result to `max_distance`, applied via `transform: translate(...)`, returning to rest on `pointerleave`/`mouseleave` via a CSS transition using `return_duration`/`return_easing`; `type: "spotlight"` is a `pointermove` listener at the `scope` level (`"element"`/`"section"`/`"viewport"`) updating CSS custom properties (`--cursor-x`/`--cursor-y`) consumed by a `radial-gradient(circle <radius> at var(--cursor-x) var(--cursor-y), <color>, transparent)` background sized by `radius` and tinted by `color`, with `follow_duration` smoothing the motion via a CSS transition on the custom properties — register them with `@property` (e.g. `syntax: '<length-percentage>'`) to make them transitionable — where the stack supports it (otherwise the glow tracks the cursor directly, no added lag). When the element carrying a `motion.scroll` entry with `type: "scrub"` is a `background_video`, drive `video.currentTime` directly from scroll progress (`progress * video.duration`) across `range` instead of interpolating CSS properties — `properties`/`from`/`to` don't apply to this case and won't be present on the token. Pause the video (don't let `autoplay`/`loop` keep advancing it on its own) while a `scrub` entry is driving its `currentTime` — otherwise native playback and the scroll-driven position fight each other. `scroll.parallax` and every `motion.cursor` entry need no special case for `background_video` — they move or tint the element as a whole exactly as already described, regardless of what's inside it. Wrap every `scroll`/`cursor` effect (not `hover`/`entrance`/`ambient` — those are unaffected) in `@media (prefers-reduced-motion: reduce)` so it's disabled there: a `scrub` element renders at its `to` (fully revealed) state instead of stuck at `from` — for a video-`scrub` element with no `to`, that means holding its last frame (`currentTime` at `video.duration`, still paused) rather than resuming playback; `parallax`/`magnetic`/`spotlight` simply render static, with no scroll- or cursor-driven offset. **A motion key can be `"type:variant"` instead of a bare type** (e.g. `cta_button:solid` vs `cta_button:ghost`) when a block has more than one skeleton element of that type — match it against that specific element's own `variant`, not every element of the type. **Don't add hover, entrance, ambient, scroll, or cursor motion to an element that has no matching entry in `motion`** — same rule as not inventing skeleton elements or borrowing another block's radii: an unlisted element stays static.
   - **Orchestrate entrance across blocks: one page load, not N independent animations.** Each block's `motion.entrance` gives raw per-element ingredients (per-element `type`/`duration`/`easing`/`delay`) — the sequence is yours to compose. When a page has multiple blocks with entrance motion, run them as a single timeline: header first (logo/nav then buttons), then hero (headline, then CTAs), then any deeper content — each block's own internal stagger preserved, but block N+1 starting its first element around when block N finishes, not at `t=0`. A page that fades in header and hero simultaneously reads as scattered micro-interactions; one that cascades reads as deliberately choreographed. If the reference tokens specify a delay that would fight this (e.g. a hero starting before the header is done), prefer the orchestration — the token gives the effect, not the page-level order.
   - **Implementing a `cursor_style` token: a replacement cursor, distinct from `motion.cursor` effects.** `motion.cursor` moves or tints existing elements (`magnetic`/`spotlight`); `cursor_style` replaces the cursor itself with a custom element (a dot, ring, or mix). Render it as a fixed-position, pointer-events-none element (or the target framework's equivalent) driven by a `pointermove` listener on the document, positioned via `transform: translate(...)` from the cursor coordinates, with the native cursor hidden (`cursor: none`) on the surfaces the reference hides it on (typically everything interactive). Apply `type` (`dot` = a filled circle of `color`; `ring` = an outlined circle of `border_color`; `mix` = a small dot plus a lagging ring, e.g. `return_*` or a short CSS transition on the ring for the trailing feel; `arrow` = a custom pointer shape drawn in SVG), `size`, `scale_hover` when it should grow over interactive elements (listen for `:hover`/`pointerover` on links/buttons, or the framework's equivalent), and `mix_blend_mode` if composited with the page. The whole effect goes inside `@media (prefers-reduced-motion: reduce)` — there it's disabled and the native cursor returns. If `hide_native` is false (or absent), keep the native cursor visible and render the custom element as an accent alongside it rather than a replacement — read the token, don't assume full replacement.
9. Persist the resolved design tokens to `.design-system.json` in the project root so follow-up requests in this conversation can reference them without calling the tool again. Include the same shape the tool returned (`_theme_anchor`, plus each block's `reference`/`tokens`/`skeleton`) and, when you made a font substitution (see step 8's anti-generic-font rule), a `_font_substitution` key recording which block's face you replaced and with what — so a follow-up run or the user can tell the token was substituted rather than shipped verbatim.
